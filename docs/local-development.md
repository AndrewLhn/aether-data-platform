# Local development

## Purpose and scope

The local stack runs the first end-to-end slice of Aether: a change in PostgreSQL becomes a committed Iceberg snapshot, with checkpoints on object storage and a repeatable way to prove both halves.

```text
PostgreSQL 17 ──WAL──> Debezium 3.7 ──> Kafka 4.2 ──> Flink SQL 1.20.5 ──> Iceberg 1.12 ──> SeaweedFS (S3)
```

Components:

- PostgreSQL 17 with logical decoding enabled;
- Apache Kafka in single-node KRaft combined mode, no ZooKeeper;
- Kafka Connect with the Debezium PostgreSQL connector;
- SeaweedFS as the S3-compatible object store for the warehouse and for Flink checkpoints;
- Apache Flink with the Iceberg runtime, submitting jobs through SQL Client.

This is a single-machine development environment. It uses plaintext Kafka, unauthenticated Kafka Connect, one broker, and local-only credentials. It is not a production deployment.

## Prerequisites

- Docker Desktop or Docker Engine with Docker Compose v2;
- `make`, `python3`, and either `curl` or `wget`;
- PyYAML for the local checks, installed by `make setup`;
- ports `5432`, `8081`, `8083`, `8333`, and `9092` free on the host;
- roughly 8 GB of Docker memory, and about 2.5 GB of disk for images on first pull;
- about 165 MB of disk for the resolved Flink libraries.

## Quick start

From the repository root:

```bash
make setup       # development dependencies for the local checks
make libs        # download and SHA-512 verify the pinned Flink libraries
make up          # start postgres, kafka, connect, seaweedfs, flink
make ps          # confirm every service reports healthy
make verify-cdc  # prove PostgreSQL -> Kafka with a freshly inserted order
make pipeline    # submit the Kafka -> Iceberg streaming job
make verify-stream
```

`make help` lists every target. `make up` builds the Flink image and resolves `.env` and the libraries first, so the sequence above is safe to re-run at any point.

The first run downloads images. Later runs reuse them.

## Local endpoints

| Service | Host address | Purpose |
|---|---|---|
| PostgreSQL | `localhost:5432` | Transactional source database |
| Kafka | `localhost:9092` | Host-facing Kafka listener |
| Kafka Connect | `http://localhost:8083` | Connector management REST API |
| Flink UI | `http://localhost:8081` | Job and checkpoint inspection |
| SeaweedFS S3 | `http://localhost:8333` | S3-compatible object-storage API |

Credentials come from `.env`. They are development-only values and must never be reused outside the local stack.

Inside the compose network the services are reachable as `postgres`, `kafka`, `connect`, `seaweedfs`, and `flink-jobmanager`. Flink and Iceberg only ever see `S3_ENDPOINT_INTERNAL`, which is what keeps the object store swappable.

## Environment file

`.env` is generated from `.env.example` by `scripts/sync-env.py`, which `make env` calls and every Docker-dependent target depends on.

The script is not a plain copy. It rewrites `.env` from the template while keeping values already present, adds keys the template introduced, and re-emits keys that exist only locally in a marked section at the end. It decides whether work is needed by comparing generated bytes with the file, so re-running it is a no-op rather than a spurious rewrite. `--check` reports drift without writing.

This exists because a stale `.env` fails in a confusing place. When the template gained the S3 variables, an `.env` created before that change made `compose up` fail with `required variable S3_ACCESS_KEY_ID is missing a value`, which reads like a compose problem and is an environment problem.

## Flink libraries

Connector and catalog JARs are not committed and are not baked into the image. They are declared in `infra/docker/flink/libs.lock` as `digest, target, url` triples and resolved by `scripts/download-flink-libs.sh` into `infra/docker/flink/lib`, which is bind mounted into the containers.

Every digest is verified before the artifact is used, and a mismatch removes the partial file and fails the run, so a tampered or truncated download cannot reach an image. The lock file itself is validated structurally before anything is fetched: a SHA-512 is exactly 128 lowercase hex characters, and a URL's basename must match its target's basename. That check exists because a digest was once transcribed by hand and committed one character too long; it is now rejected in milliseconds instead of after a 5.6 MB download.

Two related targets:

```bash
make verify-libs   # re-download every artifact and compare real digests
make verify-java   # report the JVM each artifact requires, from its bytecode
```

`verify-java` reads the class file major version of every entry in each JAR and compares the maximum against the `FROM` line of the Flink Dockerfile. It handles multi-release JARs correctly: `META-INF/versions/N` entries are excluded unless the runtime is at least N, because below that version the JVM loads the base entry instead. Without that, `iceberg-flink-runtime` reports Java 21 instead of its real floor of Java 17.

Flink's own S3 filesystem plugin ships inside the base image under `/opt/flink/opt` and is enabled at build time. The RocksDB state backend needs nothing: as of Flink 1.20 it is bundled in `flink-dist`, not shipped as an opt-in plugin.

## The streaming pipeline

`services/streaming/sql/pipeline.sql.in` is the single source of truth. It registers the Iceberg catalog, creates the Kafka source and the Iceberg sink, and starts the continuous insert.

It is a template. SQL Client has no variable substitution and credentials do not belong in git, so `services/streaming/docker/render-sql.sh` expands an explicit allowlist of variables at container start. A missing variable is a hard error naming it, and a placeholder left unresolved after substitution fails the run; both are preferable to an empty string interpolated into a `CREATE CATALOG`.

The mounted JARs are symlinked into `/opt/flink/lib` at container start by `prepare-runtime.sh`. They cannot be mounted onto `lib` directly, because a bind mount replaces the directory and would hide every JAR the base image ships. Leaving them in `/opt/flink/usrlib` does not work either: Flink adds `usrlib` to the user-code classloader only for `flink run` submissions, and SQL Client builds its classpath from `lib` and `opt`, so a catalog factory sitting in `usrlib` is invisible to it.

`make pipeline` submits through a one-shot `pipeline-submit` service rather than from inside the JobManager. A rejected job then shows up as a failed one-shot container with a readable log instead of a crash-looping cluster, and resubmitting does not restart Flink. The service is behind a compose profile, so a plain `make up` does not resubmit it.

## Verify the CDC slice

```bash
make verify-cdc
```

The script starts the stack if needed, registers the connector idempotently, waits for its task to become `RUNNING`, starts a consumer at the latest offset, inserts a row into `public.orders`, and passes only when the consumer output contains that row's unique `external_order_reference`. A successful run ends with:

```text
CDC verification passed: cdc-verification-20261026T212737Z was emitted to aether.public.orders.
```

The inserted order is deliberately left in PostgreSQL so the event trail stays inspectable.

## Verify the streaming slice

```bash
make verify-stream
```

This reports rather than asserts, and always exits 0, because its purpose is to produce a complete picture in one pass: cluster slots, the job list, per-job checkpoint counts and full exception stacks, connector state, topic end offsets, the object-store bucket listing, the rows the `JdbcCatalog` wrote into PostgreSQL, and the TaskManager log filtered to the relevant lines. A healthy pipeline shows `"state":"RUNNING"`, a growing `completed` checkpoint count, and `no exceptions recorded for this job`.

A committed snapshot looks like this in the TaskManager log:

```text
IcebergFilesCommitter - Checkpoint 1 completed. Attempting commit.
CommitSummary{dataFilesCount=1, dataFilesRecordCount=3, ...}
SnapshotProducer - Committed snapshot 9046756570855116756 (BaseRowDelta)
```

Related targets:

```bash
make jobs           # list jobs, warn if the pipeline was submitted more than once
make cancel-jobs    # cancel every job on the cluster
make doctor         # full diagnostic dump when the stack will not come up
```

`make jobs` exists because submitting twice is easy and silent. Two writers into one Iceberg table do not fail; they both commit.

## Query the lakehouse

```bash
make sql-client
```

```sql
SET 'execution.runtime-mode' = 'batch';
SELECT * FROM `aether_catalog`.`ecommerce`.`orders`;
SELECT snapshot_id, committed_at, operation FROM `aether_catalog`.`ecommerce`.`orders$snapshots`;
```

Metadata tables need backticks and full qualification. `$` is not valid in a bare identifier, and omitting the backticks produces a parse error that does not mention the `$`.

Queries run in batch mode. In streaming mode a `SELECT` becomes a continuous job and does not return a result set.

## E-commerce source schema

PostgreSQL starts with `wal_level=logical`, `max_wal_senders=10`, and `max_replication_slots=10`. The initialization scripts create a dedicated `debezium` role with replication and read permissions, then create `customers`, `orders`, `payments`, and `inventory`, seed them with synthetic data, and create `aether_cdc_publication` for exactly those tables. The connector uses that publication instead of being granted broad DDL or publication-management privileges.

## The CDC data contract

Three connector properties exist because of the consumer, not because of PostgreSQL. They look like tuning and are load-bearing. `infra/docker/connectors/README.md` records each one with the failure it prevents:

- `decimal.handling.mode: string` — the default encodes `NUMERIC` as base64 bytes, which Flink's `debezium-json` cannot turn back into a `DECIMAL`;
- `tombstones.on.delete: false` — `debezium-json` does not expect null-valued tombstones;
- timestamps arrive as RFC 3339, so the reader needs `timestamp-format.standard=ISO-8601` and `TIMESTAMP_LTZ` columns.

Changing any of them changes what the reader must expect, and it is not retroactive: records already in a topic keep the encoding they were written with.

## Stop and reset

Stop the containers and keep the data:

```bash
make down
```

Destroy every volume and start over:

```bash
make reset
```

`make reset` permanently deletes the local PostgreSQL, Kafka, and SeaweedFS volumes. Never run it against an environment holding data you need.

Reset is also the way to apply a change to an Iceberg column type. `CREATE TABLE IF NOT EXISTS` will not alter a table that already exists, and Iceberg does not promote `timestamp` to `timestamptz`, so a schema change of that kind needs the table dropped or the stack reset.

## Known benign warnings

These appear in healthy runs and are not defects:

| Warning | Why it is safe to ignore |
|---|---|
| `IAMInstanceCredentialsProvider.<init>` with an s3a stack trace | s3a walks a credential-provider chain; the static keys are configured and checkpoints commit |
| `Cannot load Dropwizard metrics` | optional dependency; Iceberg logs and continues |
| `Error while loading kafka-version.properties` | an artifact of connector shading |
| `Unable to call register for ArrowFormatModels / SparkFormatModels` | Iceberg probes optional Arrow and Spark integrations that are absent |
| `Cannot locate configuration: hadoop-metrics2*.properties` | s3a metrics configuration |
| `JDBC catalog is initialized without view support` | views are not used; `jdbc.schema-version=V1` enables them |
| `Unknown module: jdk.compiler specified to --add-exports` | the base image passes JVM flags for a module this JDK build does not expose |

Anything else in the TaskManager log is worth reading. `make doctor` collects it, with secrets redacted.

## Troubleshooting

Start with `make doctor`. It gathers, in one pass: container health with the last probe output and exit code, the rendered Flink configuration, enabled plugins and mounted libraries, a direct probe of the REST endpoint from inside the container, full exception stacks for unhealthy or exited containers, and any orphan containers left by an earlier compose file.

Two habits that cost time here:

- A truncated exception is worse than none. The interesting frame is usually below the last `Caused by` that fits on a screen.
- A deserialization failure that names a field is a configuration question, not a data question. Check the contract in `infra/docker/connectors/README.md` before inspecting records.
